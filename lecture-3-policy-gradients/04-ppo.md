# Proximal Policy Optimization (PPO)

A slide-by-slide breakdown, based on `source/lecture-3-policy-gradients-slides.md` and `source/lecture-3-policy-gradients-transcript.md`. Follows on from `03-reinforce-and-rloo.md`. ---

## Where this fits

REINFORCE and RLOO compute an advantage, take **one** gradient step, then throw the batch away and generate a new one. PPO changes three things:

| | What PPO adds | Why |
|---|---|---|
| **1** | **Several gradient steps per batch** (typically 2–4) | Generating completions is expensive, so get more learning out of each batch |
| **2** | **The ratio ρ + clipping** | Makes those extra steps safe: each token's probability can only move so far per batch |
| **3** | **A trained value model (critic) + GAE** | A smarter baseline that gives each token its *own* advantage, not one number copied to every token |

1 and 2 are PPO's core ideas. 3 isn't strictly part of the PPO algorithm, but it's how PPO is almost always implemented (Lambert: "not necessarily a core idea, but a core implementation").

**What doesn't change:** it's still "make good tokens more likely, bad tokens less likely, scaled by advantage." On the first gradient step of each batch, PPO's update is the same policy-gradient step from `01`. Everything new kicks in from the second step onward.

This is the hardest section of the lecture. The parts you can safely treat as black boxes are marked.

---

## Slides: "If REINFORCE is so simple, why PPO?"

### On-policy vs. off-policy (vocabulary)

- **On-policy** (everything in this lecture): generate fresh completions from the *current* model every batch, learn from them, discard them.
- **Off-policy** (e.g. DQN, DeepMind's Atari work): store old experience in a buffer and reuse it many times.

On-policy is simpler and more stable, but wasteful, because each batch is used once and thrown away.

### The real problem: step size

Plain policy gradient is **very sensitive to step size** (the learning rate), because its gradient estimates are noisy:
- **Step too small:** learning is painfully slow.
- **Step too large:** training collapses. Lambert: "you'll have progress, and then bam, it'll come down."

A noisy gradient plus a big step means you sometimes take a big step in a bad direction, and since the next batch is generated by that damaged model, it's hard to recover.

### TRPO → PPO

- **TRPO** (Trust Region Policy Optimization, 2015) fixed this with a hard mathematical limit on how far the policy can move per update. It works, but needs expensive, complicated optimization math.
- **PPO** (2017) gets similar stability with a much simpler trick (**clipping**), and because each update is kept conservative, you can safely take **multiple** gradient steps per batch. It became the industry-standard RL algorithm.

---

## Slide: "What can we do with more conservative gradients?"

If each step is guaranteed to be small and safe, you can **take several steps on the same batch** and extract more learning from it.

But that creates two new problems:
1. **How do you keep the *total* movement under control across several steps?** (→ clipping)
2. **After the first step, the batch is stale.** It was written by the model *before* the update, not the current one. Is the gradient still valid? (→ the ratio ρ)

### The timing (this is the key picture)

```
generate batch with policy  ──►  π_old  = the policy at this moment (snapshot)
                                  │
   inner step 1:  policy = π_old            ← batch is fresh, ordinary policy gradient
   inner step 2:  policy = π_old + 1 update ← batch is now slightly stale
   inner step 3:  policy = π_old + 2 updates← staler
   inner step 4:  policy = π_old + 3 updates
                                  │
throw batch away, generate a new one with the updated policy (it becomes the new π_old)
```

This is why `02` separated π_old (the start of *this batch*) from π_ref (the start of *the whole run*).

### How do you get several gradients from one batch? *(my addition)*

It's **multiple epochs over the same data**, which you know from supervised learning.

| | Supervised learning | RL |
|---|---|---|
| 1 pass over the data | 1 epoch | **REINFORCE / RLOO:** one gradient step, then throw the batch away |
| Several passes over the same data | multiple epochs | **PPO:** 2–4 gradient steps on the same batch, then throw it away |

```
generate batch (e.g. 64 prompts × 4 = 256 completions), compute advantages (fixed)

pass 1:  forward pass on the batch with current weights → loss → backward → gradient #1 → update
pass 2:  forward pass on the SAME batch with the updated weights → gradient #2 → update
pass 3:  same batch again → gradient #3 → update
pass 4:  same batch again → gradient #4 → update

throw the batch away, generate a new one
```

**Why the gradient comes out different each pass:** the data is the same, but the **weights changed**, and the gradient depends on the weights (the same reason epoch 2 differs from epoch 1). On each pass the log-probs for the same tokens have shifted, so ρ has changed, and some tokens have hit the clip limit and dropped out.

**Why RL needs clipping for this and supervised learning doesn't:** supervised data is fixed ground truth. RL data was **written by the model** as it was at the start of this batch. After one update you're training the new model on the old model's answers, and the more passes you take, the less those answers reflect what the model would write now. The ratio corrects for the mismatch, and clipping stops each token after about ±20% of movement. Together they make passes 2–4 safe.

**Detail:** each pass is often split into **minibatches** (e.g. 256 completions as 4 chunks of 64, one gradient step per chunk). So "K steps per batch" can mean K passes × several minibatch steps each. Same idea: several updates from one round of generation.

## Slide: "PPO core idea 1: Constrained updates"

Large gradient steps can wreck the policy (instability, over-optimization). The fix is a **trust region**: only trust the batch's gradient within a small neighborhood of the policy that generated it, and limit how far the policy can move inside one batch.

The intuition: the batch tells you what's good *near* π_old. The further the policy moves from π_old, the less that batch tells you, so stop before you get too far.

---

## Slide: "PPO core idea 2: Importance sampling"

To measure "how far has the policy moved from π_old?", PPO looks at each token in the batch and compares the two models' probabilities for it:

```
ρ_t = π_θ(token_t) / π_old(token_t)
      ^^^^^^^^^^^^   ^^^^^^^^^^^^^^
      current model   model that wrote the batch (saved at generation time)
```

| ρ | Meaning |
|---|---|
| **= 1** | The current model and π_old agree on this token. No change yet. |
| **> 1** | The current model now finds this token **more** likely than when it was written |
| **< 1** | The current model now finds this token **less** likely |

**Example:** π_old gave "4" a probability of 0.30. After two inner steps, the current model gives it 0.36. ρ = 0.36 / 0.30 = **1.2**, so "4" is 20% more likely than it was at the start of this batch.

### Why a ratio fixes the stale batch *(the idea, not the proof)*

The batch's completions appear at the rate π_old would write them, not the rate the current model would. The ratio **reweights** each sample to correct for that: tokens the current model now likes more get counted a bit more, tokens it likes less get counted less.

It's like adjusting an old poll after the population has shifted, instead of running a new poll. This trick, "importance sampling", is standard statistics, and the slide's point is just that it lets you keep using π_old's samples.

### How ρ is computed in practice

- **π_old's log-probs** are saved once, at generation time (step 2 of the loop). They don't change during the inner steps.
- **The current model's log-probs** are recomputed with a forward pass at every inner step, since the model changes after each step.
- ρ = exp(current log-prob − old log-prob), one number per token.

On inner step 1 nothing has changed yet, so **ρ = 1 for every token**.

---

## Slide: "The surrogate objective"

Plugging the ratio into the policy-gradient recipe gives:

```
J(θ) = average over tokens of ( ρ_t × advantage_t )
```

"Surrogate" means a stand-in objective. You maximize this instead of the true objective because it's computable from π_old's samples.

It's the same shape as before: some probability term times "how good was it." In fact, at ρ = 1 (inner step 1), its gradient is exactly the policy gradient from `01`, so PPO's first step is an ordinary policy-gradient step.

**The problem:** nothing stops ρ from running away. If a token has a positive advantage, maximizing ρ × advantage says "keep making it more likely, forever." Over several inner steps the policy could move far from π_old, where the batch's information is no longer reliable. That's the large-step collapse again.

---

## Slide: "The PPO clipped objective"

PPO's fix is to **clip** the ratio:

```
J(θ) = average of  min( ρ_t × A_t ,  clip(ρ_t, 1−ε, 1+ε) × A_t )
```

with ε (epsilon) typically **0.1–0.2**.

You don't need to parse the min/clip algebra. **What it does:**

> **Each token's probability may move up to ±ε (e.g. ±20%) away from π_old in the helpful direction during this batch. Past that, its gradient becomes zero, and that token stops pushing on the weights for the rest of the batch.**

The trust region is the band **1 − ε ≤ ρ ≤ 1 + ε** (e.g. 0.8–1.2). The `min` always picks the more cautious of the two versions.

(Naming note: the PPO paper calls this L^CLIP, using L as in "loss," but it's an objective you *maximize*, so the slides call it J.)

---

## Slides: Positive, negative and zero advantage

The clipping behaves differently depending on whether the token was good or bad. Use ε = 0.2.

### Positive advantage (good token: make it more likely)

Walk through the inner steps for "4" with advantage **+0.5**:

| Inner step | ρ (current ÷ old) | Case | Gradient |
|---|---|---|---|
| 1 | 1.00 | inside trust region | normal, push "4" up |
| 2 | 1.10 | inside | normal, push up |
| 3 | 1.25 | **above 1 + ε = 1.2** | **zero: clipped.** "4" already moved enough this batch |
| 4 | 1.25 | above | zero (stays put unless other updates move it) |

And the case that isn't clipped: if other tokens' updates **accidentally made "4" less likely** (ρ = 0.75, below 0.8), the gradient is **normal**, so the policy is pushed back toward the good token.

### Negative advantage (bad token: make it less likely)

"fish" with advantage **−0.5**:

| Inner step | ρ | Case | Gradient |
|---|---|---|---|
| 1 | 1.00 | inside | normal, push "fish" down |
| 2 | 0.90 | inside | normal, push down |
| 3 | 0.75 | **below 1 − ε = 0.8** | **zero: clipped.** "fish" already dropped enough this batch |

If "fish" accidentally became **more** likely (ρ = 1.3), the gradient is normal and pushes it back down.

### Zero advantage

The token was exactly as good as expected, so the objective is 0 and there's **no update**, whatever ρ is.

### Slide: "Clipping summary"

| Advantage | Inside trust region | Outside trust region |
|---|---|---|
| **> 0** (good) | normal gradient (reinforce) | zero if ρ > 1 + ε (already pushed up enough) |
| **< 0** (bad) | normal gradient (suppress) | zero if ρ < 1 − ε (already pushed down enough) |
| **= 0** | no update | no update |

The key phrase from the slide: **clipping is one-sided.** It stops a token once it has moved enough in the *helpful* direction, but it **never blocks a correction** if the token drifted the *wrong* way. Progress is capped, mistakes are always fixable.

### Common confusion: what gets clipped, and by how much?

**The advantage is never clipped.** It stays fixed for the whole batch. What gets clipped is **the ratio ρ**: how much this token's probability has changed since the batch was generated.

| | What it measures | Changes during the inner loop? |
|---|---|---|
| **Advantage A** | How good was this token? | ❌ Fixed, computed once before the inner loop |
| **Ratio ρ** | How much has this token's probability moved since the batch was written? | ✅ Yes, updated every inner step |

Clipping acts as a per-token **off switch**, not a shrink factor. Once a token has moved far enough in the helpful direction, its gradient goes to **zero**:

```
"4", advantage = +0.5 (stays +0.5 the whole time), ε = 0.2

inner step 1:  ρ = 1.00   inside band (0.8–1.2)   → gradient ON  (full strength, weighted by +0.5)
inner step 2:  ρ = 1.10   inside band             → gradient ON
inner step 3:  ρ = 1.25   past 1.2                → gradient OFF (this token is done for this batch)
```

Inside the band a token gets the normal policy-gradient push. Past the edge in the helpful direction it gets nothing. Past the edge in the wrong direction, the gradient stays on so the mistake can be corrected.

**How much to clip by:** ε is a **hyperparameter**, like the learning rate, chosen by experience, not derived from the math. The PPO paper tried several values and 0.2 worked best in their experiments. 0.1–0.2 has been standard ever since.

| ε | Each token may move per batch | Effect |
|---|---|---|
| Smaller (0.1) | ±10% | Safer, more stable, slower learning |
| Larger (0.3) | ±30% | Faster learning, more risk of the collapse PPO exists to prevent |

ε also interacts with K (inner steps) and the learning rate. With more steps or bigger steps, tokens hit the edge of the band sooner, so people tune these together.

*(Preview beyond these slides: some newer GRPO variants use a different ε for the top and bottom of the band, letting good tokens rise more than bad tokens fall.)*

> **One sentence:** clipping doesn't change how good a token was. It limits how far each token's probability is allowed to move in one batch: about ±20%, a number picked because it works well in practice.

### Slide: "PPO clipping visualized"

*(The plot isn't in the folder. Here's what it shows, from the transcript.)*

Two graphs with ρ on the x-axis and the objective (what PPO maximizes) on the y-axis:
- **Positive advantage:** the line rises as ρ increases, then goes **flat** at 1 + ε. Flat means no gradient, so no more incentive to push further.
- **Negative advantage:** the line goes flat below 1 − ε and slopes elsewhere, a mirror image.

Lambert's summary: "if you're in the trust region, you have the normal policy gradient. If you're not, you stop." **That is what lets PPO take several gradient steps per batch safely.**

## Slide: "The value function (critic)"

This is PPO's third addition (the "core implementation" part): a **second neural network trained alongside the policy**, called the **value model** or **critic**, V_φ.

| | |
|---|---|
| **What it predicts** | At each token position: "from here, how much (shaped) reward do I expect this completion to end up with?" |
| **What it is physically** | Usually another full LLM-sized model, initialized from the reward model or SFT model, with an output head that produces **one number per token** instead of next-token probabilities |
| **How it's trained** | **Plain supervised regression (MSE).** Target = the reward the completion actually ended up getting (after the KL penalty). Loss = ½(prediction − actual)². |
| **What it's for** | A **learned baseline**: "what did we expect from this point?", per token, instead of one per-prompt average |

You already know the training method: it's regression from your ML course. Each batch provides (position in completion → actual outcome) examples, and the critic learns to predict outcomes.

Lambert's framing: in REINFORCE/RLOO the baseline is estimated **empirically** (by sampling multiple answers). In PPO it's **learned** (a model predicts it), and the samples are used to train that model. You trade compute and complexity for a better baseline.

---

## Slide: "How PPO-RLHF gets token-level credit"

The problem from `03`: one reward for the whole completion, copied to every token, so "The" gets the same credit as "4."

PPO's answer:
1. **Every token gets a small per-token reward from the KL penalty:** r_t = −β·KL_t (from `02`).
2. **The final token also gets the reward model's score:** r_T = R − β·KL_T.
3. **The critic + GAE spread credit backward**, so each token gets its *own* advantage depending on whether it made things better or worse.

So the per-token rewards come from the KL penalty and the final score, and the critic is what turns them into per-token **credit**.

---

## Slide: "Advantage estimation"

The simplest critic-based advantage:

```
A_t = G_t − V(s_t)
      ^^^   ^^^^^^
      what actually happened from token t onward
            what the critic expected at token t
```

This is the "reward − baseline" idea again, now per token with a learned baseline.

Two benefits:
- **Centering** reduces noise (same as every baseline).
- **Credit assignment:** with per-token predictions, each token can get a different advantage.

This version (actual outcome − prediction) is the "Monte Carlo" advantage: unbiased but noisy. TD and GAE (next slides) trade a little bias for less noise.

---

## Slide: "The TD residual"

```
δ_t = r_t + V(s_{t+1}) − V(s_t)        (γ = 1 for LLMs, so it drops out)
```

In plain words: **how much did the critic's prediction change because of token t?**

- V(s_t): expected outcome *before* writing token t
- r_t + V(s_{t+1}): reward for token t (usually just a tiny KL penalty) plus the expected outcome *after* writing it

**Example: why this fixes credit assignment.** Solving "What's 17 × 3?":

| Token | Critic before | Critic after | δ (≈ after − before) | Meaning |
|---|---|---|---|---|
| "The" | 0.50 | 0.50 | **0.0** | filler, didn't change the outlook, so no credit |
| "answer" | 0.50 | 0.50 | **0.0** | no credit |
| "is" | 0.50 | 0.50 | **0.0** | no credit |
| "51" | 0.50 | 0.95 | **+0.45** | this token made the answer right, so it gets the credit |

If the answer had been "54", the critic would drop after that token (0.50 → 0.05, δ = −0.45), and only that token would be blamed.

This is "1-step" because it only looks one token ahead and trusts the critic for the rest:
- **Low variance:** it doesn't depend on the randomness of everything sampled afterward.
- **Can be biased:** if the critic is wrong, δ is wrong.

## How does the critic know which tokens matter? *(my addition, not on the slides)*

It learns which tokens matter by watching which partial answers tend to end well. The critic's job is to look at a half-written answer and predict how it will end. A token earns credit if the prediction jumps after it.

### An analogy: a live win-probability meter

Sports broadcasts show a win-probability meter during a game. It sits near 50%, and after a big play it jumps to 85%. Everyone can see that play was the one that mattered, because the meter moved. Routine plays barely move it.

The critic is a win-probability meter for a half-written answer, and the TD residual is "how much did the meter move on this token?"

### How the critic learns its predictions

It's plain regression. For every completion in every batch, each position becomes a training example:

```
input:  the text so far (prompt + tokens up to position t)
target: the reward this completion actually ended up getting
```

Five completions for "What's 17 × 3?" (51 is correct):

| Completion | Final reward |
|---|---|
| "The answer is 51" | 1 |
| "The answer is 54" | 0 |
| "The answer is 51" | 1 |
| "The answer is 48" | 0 |
| "It's 51" | 1 |

What the critic is trained to predict for each partial answer:

| Partial answer the critic sees | Targets it gets trained on | What it learns to predict |
|---|---|---|
| "The answer is" | 1, 0, 1, 0 | **0.5** (could go either way) |
| "The answer is 51" | 1, 1 | **1.0** |
| "The answer is 54" | 0 | **0.0** |

Nobody told it that 51 is correct. It learned from outcomes: "The answer is" is followed by success half the time, and "…51" is followed by success every time.

### Turning predictions into per-token advantages

The TD residual reads off the jumps:

```
            before   after   jump (≈ advantage)
"The"        0.5      0.5      0.0    ← meter didn't move: no credit
"answer"     0.5      0.5      0.0
"is"         0.5      0.5      0.0
"51"         0.5      1.0     +0.5    ← meter jumped: this token gets the credit
"54"         0.5      0.0     −0.5    ← meter crashed: this token gets the blame
```

Credit goes to the tokens where the predicted outcome changed.

### "But the reward only exists once the answer is done. How can it predict mid-answer?"

It learns by observing. For the answer being written right now, the critic doesn't know how it will end. It's **guessing based on past answers it has seen finish.**

**A weather forecaster:** "70% chance of rain tomorrow" doesn't mean the forecaster knows tomorrow's weather. Over thousands of past days, they've seen that days with conditions like these turned out rainy about 70% of the time. The critic is the same:
- **Past batches:** thousands of completions finished and got rewards. Every partial answer from them became a training example: (text so far → the reward that answer *eventually* got).
- **Now:** the critic looks at a new partial answer and says "partial answers like this one usually ended up around 0.5."

So the critic never predicts *this* answer's reward. It predicts what answers that started like this one usually got.

**When the critic runs:** not while the policy is writing. It runs after the completion is finished, covering every position at once, but at each position it can only see the text up to that point:

```
step 2: policy writes the full completion       "The answer is 51"
step 3: reward model scores it                   → 1.0
step 5: critic reads the finished completion, one prediction per position:

        position 1: sees "The"                → 0.5
        position 2: sees "The answer"         → 0.5
        position 3: sees "The answer is"      → 0.5
        position 4: sees "The answer is 51"   → 1.0
```

It doesn't peek ahead because LLMs read left to right. At each position the model only sees earlier tokens, the same mechanism that stops a language model from seeing the next word while predicting it. So each prediction is an honest "from here, how will it go?", even though the full text is there.

**The full cycle:**

```
batch 1:  critic is clueless (predicts ~same everywhere)
          → advantages are mostly noise
          → afterwards: learn from batch 1's (partial answer → final reward) examples

batch 2:  critic slightly better
          → advantages slightly more meaningful
          → afterwards: learn from batch 2

...

batch 500: critic has seen ~many thousands of finished answers
           → it has a decent sense of which partial answers tend to end well
```

The critic and the policy improve together. The critic starts from the reward model's weights, which gives it a head start because the reward model already knows what good *finished* answers look like. Judging *partial* answers is a new skill it has to learn.

### Why this works on real data

- **The critic is an LLM itself** (initialized from the reward model or the SFT model). It already understands text, so it doesn't need to have seen "17 × 3" before. It can generalize that "the correct product appears" means things are going well, the same way it would for any regression on text features.
- **This is statistics over many batches.** Prefixes that appear in both good and bad answers settle at the average. Tokens that consistently come before good or bad outcomes get pulled up or down.

### The catch

- **Early in training the critic is bad:** it predicts roughly the same value everywhere, so the jumps are noise. That's the "bias" in the TD/GAE slides: if the meter is broken, the credit is wrong.
- **It's chasing a moving target.** The critic learns from the policy's answers while the policy keeps changing, so it's always slightly out of date.
- **GAE's λ ≈ 0.95 hedges against this.** It mixes in the actual final outcome so a bad critic doesn't fully mislead the policy.

That fragility, plus the cost of a fourth model, is a big part of why GRPO dropped the critic and went back to RLOO-style "one number per answer."

### Timing

- **Step 5:** the *current* critic makes its predictions, and GAE turns the jumps into per-token advantages. These are fixed for this batch.
- **Inner loop:** the critic gets a regression update toward the actual outcomes in this batch, so it's slightly better at predicting for the next batch.

## Slides: "GAE" (Generalized Advantage Estimation) *(safe to black-box)*

Lambert himself says: "Mathematically, this is very complicated and honestly, it takes me a while to still grok this." Here's the idea only.

There's a spectrum of ways to compute a token's advantage:

| Version | How it works | Variance | Bias |
|---|---|---|---|
| **1-step (TD)** | Look one token ahead, trust the critic for everything after | Lowest | Highest (if the critic is wrong) |
| **k-step** | Look k tokens ahead using real rewards, trust the critic after that | In between | In between |
| **All the way (Monte Carlo)** | Use the actual final outcome, critic only for the baseline: G_t − V(s_t) | Highest | None |

**GAE blends all of them** with a weighted average, controlled by one dial, **λ (lambda)**:

| λ | Behavior |
|---|---|
| 0 | Pure 1-step TD: trust the critic fully |
| **0.95** | **Typical default for LLMs**: mostly trust nearby steps, but blend in the real outcome |
| 1 | Pure Monte Carlo: ignore the critic's intermediate predictions |

The slide also notes that a poorly trained critic can make even low-λ estimates unreliable. The whole thing is only as good as the critic.

**Takeaway:** GAE is a dial between "trust the critic" (less noise) and "trust what actually happened" (no bias). You set λ ≈ 0.95 and move on.

**Refinement (from lecture 4):** the TD-residual tables above show credit landing *only* on the token where the critic jumped. That's the λ = 0 picture. With λ = 0.95, credit also **leaks backward** to earlier tokens, fading by 5% per token (over roughly the ~20 tokens before the jump). See the worked GAE example in `../lecture-4-implementing-rl/02-ppo-implementation.md`.

## Slide: "PPO-RLHF: Full policy objective"

```
J(θ) ≈ L^CLIP(θ) − β × KL(π_θ ‖ π_ref)
```

**Two layers of regularization, two different jobs:**

| | Clipping | KL penalty |
|---|---|---|
| **Compares against** | π_old (start of **this batch**) | π_ref (start of **the whole run**) |
| **Limits** | How far each token moves **per batch** | Total drift **across all of training** |
| **Protects against** | Unsafe steps from a stale batch | Reward hacking / gibberish |
| **Where it lives** | In the loss (inner steps) | In the reward (before advantages) |
| **Origin** | Part of the original PPO algorithm | Added for language models (RLHF) |

They're **not redundant**. Clipping keeps each batch's steps safe. KL keeps the whole run anchored.

## Slide: "PPO training loop (conceptual)"

This is the full loop with timing made explicit. Compare it to the single-step loop in `00`.

```
policy π_θ ─ trained       value model V_φ ─ trained
reference π_ref ─ frozen   reward model ─ frozen

for each batch:                                        ── OUTER LOOP ──
    1. sample prompts; generate completions with the policy
       save each token's log-prob                       ← these ARE "π_old" (frozen for this batch)
    2. score with reward model → R
    3. reference log-probs → per-token KL               (frozen π_ref)
       per-token rewards: −β·KL_t, plus R on the last token
    4. value model predicts V at every token            (computed ONCE, before any updates)
       GAE → one advantage per token
       (advantages are now FIXED for this batch)

    for k in range(K):  # K ≈ 2–4                       ── INNER LOOP ──
        5. forward pass: current policy log-probs for the same tokens
        6. ρ_t = exp(current log-prob − old log-prob)   (= 1 on the first inner step)
        7. policy loss = −clipped(ρ_t × A_t), averaged
           value loss  = MSE(V prediction, actual return)
        8. backward → gradients for policy AND value model
        9. optimizer step → ★ policy and value model CHANGE ★

    10. discard the batch; the next batch's generation becomes the new π_old
```

### Timing points that trip people up

- **Advantages are computed once per batch** (step 4), before the inner loop, and stay fixed. Only ρ changes inside the inner loop.
- **π_old isn't a separate model in memory.** It's the log-probs saved at step 1. "Syncing π_old ← π_θ" (the slide's last step) just means the next batch is generated by the updated policy and its log-probs are saved.
- **Inner step 1 is plain policy gradient** (ρ = 1, nothing clipped). Clipping only matters on steps 2+.
- **Two models update in the inner loop**: the policy (clipped objective) and the critic (regression). That's the "two learning blocks" Lambert mentions.
- In real implementations the batch is usually split into minibatches, and "K" means K passes (epochs) over them. The idea is the same.

## Slide: "PPO: Four models in memory"

| Model | Purpose | Updates? |
|---|---|---|
| **Policy** π_θ | Generates completions | ✅ Yes |
| **Value model** V_φ | Predicts expected return per token (critic) | ✅ Yes |
| **Reference** π_ref | KL anchor | ❌ Frozen |

That's four LLM-sized models in GPU memory, **two of them being trained** (with gradients and optimizer state, which roughly multiplies their memory cost). This is expensive, and it's a key reason simpler methods like GRPO took over (next section). There are tricks to cut this down, like one model with two output heads, but this is the baseline setup.

## The whole section in four lines

1. **Problem:** policy gradient is noisy and step-size sensitive, and on-policy batches are expensive to generate. PPO wants to take several steps per batch without blowing up.
2. **Ratio + clipping:** ρ = current prob ÷ prob when the batch was written. Each token may move about ±20% in the helpful direction per batch, then its gradient goes to zero. Corrections in the wrong direction are never blocked.
3. **Critic + GAE:** a second model, trained by regression, predicts the expected outcome at each token. "Did this token raise or lower the prediction?" gives each token its own advantage, which fixes the credit-assignment problem.
4. **Cost:** two layers of regularization (clipping per batch vs. π_old, KL per run vs. π_ref), four models in memory, two of them trained. That expense is why GRPO came next.
