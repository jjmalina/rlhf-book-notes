# Training Loop Timeline

A map for Lecture 3. The lecture presents each piece as a standalone equation. This doc shows **when** each piece runs, **which version** of each model it uses, and **what changes** at each point. It's updated as each section of the notes adds new pieces.

Covers so far: `01-policy-gradients-core-intuitions-and-maths.md`, `02-wiring-rlhf-for-language-models.md`, `03-reinforce-and-rloo.md`, `04-ppo.md`, `05-grpo-and-modern-variants.md` (the whole lecture).

---

## The cast

| Model | What it is | Changes during training? |
|---|---|---|
| **Policy** π_θ | The LLM being trained | ✅ Yes, once per step (at the optimizer step) |
| **Reference** π_ref | Frozen copy of the policy from the start of the run (the SFT checkpoint) | ❌ Never |
| **Reward model** | Scores completions (in RLVR, replaced by a verifier program) | ❌ Never (trained in an earlier stage) |
| **Value model** V_φ *(PPO only)* | The critic: predicts expected reward at each token | ✅ Yes, trained alongside the policy by regression |

## Glossary

| Term | Symbol | One number per… | Plain meaning |
|---|---|---|---|
| **Weights / parameters** | θ | – | The model's knobs. Training changes these. |
| **Log-prob** | log π_θ(a \| s) | token (summed per completion) | Log of the probability the model gave the token it picked |
| **Grad-log-prob** ("which knobs") | ∇_θ log π_θ(a \| s) | **weight**: a vector, one entry per weight, for each completion | How *sensitive* this completion's probability is to each weight: "nudge this weight up and the answer gets more (or less) likely." Not a probability: entries can be positive, negative or ~0. Also called the **score function**, or **characteristic eligibility** (REINFORCE, 1992). Same gradient as cross-entropy in SFT, with the model's own output as the label. |
| **Reward** | R | completion | The score from the reward model or verifier |
| **Baseline** | b | prompt (or token, with a critic) | "What we expected": group average, leave-one-out average, or a critic's prediction |
| **Advantage** ("how good") | A, Ψ | **completion** (REINFORCE/RLOO/GRPO) or **token** (PPO + GAE) | Reward − baseline: better or worse than expected. Scales the *whole* grad-log-prob vector for that completion. |
| **Policy gradient** | ∇_θ J | weight (one vector for the whole batch) | Average over the batch of (advantage × grad-log-prob). The direction to move every weight. |
| **Update / optimizer step** | θ ← θ + … | – | The optimizer (e.g. Adam) turns the gradient into an actual change to the weights |
| **KL penalty** | β·KL_t | token | log-prob(policy) − log-prob(reference): drift from the start of the run, subtracted from the reward |
| **Ratio** *(PPO)* | ρ | token | prob now ÷ prob when the batch was written (π_old). 1 = unchanged. |
| **Clip range** *(PPO)* | ε | – (a setting, ~0.1–0.2) | How far ρ may move (e.g. 0.8–1.2) before that token's gradient switches off. The advantage itself is never clipped. |

How the pieces combine:

```
for each completion:   advantage (one number)  ×  grad-log-prob (one vector, entry per weight)
average over batch  →  policy gradient (one vector)  →  optimizer  →  weights change
```

In code you never build these vectors yourself. `loss = −(advantages * seq_log_probs).mean(); loss.backward()` makes autograd compute the advantage-weighted average directly.

## Before training starts

```
SFT model ──copy──► policy π_θ        (will be trained)
          └─copy──► reference π_ref   (frozen forever)
reward model                          (already trained, frozen)
```

At this moment the policy and the reference are **identical**.

---

## The loop in five sentences

> 1. For each prompt, its several outputs are compared to get **one advantage per output**.
> 2. Each output's "which knobs" vector is **weighted by its advantage**.
> 3. All the weighted vectors in the batch (across all prompts) are **averaged into one gradient**. (The advantages themselves aren't averaged. The weighted vectors are.)
> 4. The optimizer uses that gradient to **update the policy**.
> 5. The **next batch** is generated by the updated policy.

That's REINFORCE and RLOO exactly. PPO repeats steps 2–4 two to four times on the same batch (with ratio + clipping) before step 5.

A **batch** = many prompts × N completions each (e.g. 64 × 4 = 256). **Advantages are per prompt** (compare within the group), and **the gradient is per batch** (average across everything).

## One training step

Every step runs in this order. Only line 7 changes any weights.

```
                                                policy π_θ      reference π_ref   reward model
──────────────────────────────────────────────────────────────────────────────────────────────
1. sample a batch of prompts                        –                 –                –
2. generate N completions per prompt            used as-is            –                –
   (save each token's log-prob)
3. score each completion → R                        –                 –           used (frozen)
4. reference log-probs for the same tokens          –            used (frozen)         –
   (one forward pass: no sampling, no gradients)
5. arithmetic on numbers from 2–4:
     KL_t       = policy log-prob − reference log-prob    (per token)
     reward     = R − β × sum(KL_t)                       (shaped reward)
     advantage  = reward − baseline                       (e.g. group mean)
6. loss = −(advantage × sum of token log-probs).mean()
   loss.backward()  → ONE policy gradient           computed          –                –
7. optimizer.step()                              ★ CHANGES ★          –                –
──────────────────────────────────────────────────────────────────────────────────────────────
→ back to 1, with the updated policy
```

### Things that trip people up

- **Everything in lines 2–6 uses the policy *before* this step's update.** The policy only changes at line 7.
- **The KL penalty is part of the reward**, so it's computed (line 5) *before* the gradient (line 6). It isn't applied afterwards.
- **The whole batch (many prompts × N completions) produces one gradient and one update.** It's not one update per completion, and not one per prompt.
- **The reward model and reference never change.** Only the policy does.
- **The "math" (derivation, log-derivative trick) doesn't appear as a step.** It only justifies why line 6's loss is the right one. At runtime, `backward()` does the work.

## How things change across steps

```
              policy π_θ                      reference π_ref     KL vs reference
step 1        = original                      original            0 (identical)
step 2        = original + 1 update           original            small
step 3        = original + 2 updates          original            a bit larger
...
step 500      = original + 499 updates        original            larger (if it has drifted)
```

- **π_ref stays fixed**, so the KL measures *total drift since the start of the run*, not the change from the last update.
- If the policy drifts a lot (for example, by exploiting the reward model), the KL grows, the shaped reward shrinks, and the leash pulls it back.

## Two different "old" models

| | Compares the policy against… | Scope | Where it's used |
|---|---|---|---|
| **π_ref** | the model at the **start of the run** | Run-level, frozen | KL penalty (step 5 above) |
| **π_old** | the model at the **start of this batch** (the one that generated it) | Batch-level, refreshed each batch | PPO's ratio ρ (see `04`) |

With one update per batch (as in the loop above), π_old is the same as the policy at the moment of the update, so it doesn't matter yet. It starts to matter when PPO takes **several** updates on one batch.

## Algorithms as variations on the step

Every algorithm runs the same loop. They differ in **how step 5 computes the baseline** and in **whether steps 6–7 repeat on the same batch**:

| Algorithm | Step 2 | Step 5 baseline | Steps 6–7 per batch | Extra trained model? |
|---|---|---|---|---|
| **REINFORCE** | any number of completions | batch average / moving average | once | none |
| **RLOO** | **K per prompt** | average of the **other K−1** for the same prompt | once | none |
| **PPO** | any | **learned value model** (critic) | **several times** (uses π_old, ratio, clipping) | value model |
| **GRPO** | **G per prompt** | group **mean ÷ std** (z-score), same prompt | 1 or several (PPO-style clipping) | none |
| **GSPO** | G per prompt | like GRPO | like GRPO, but **one ratio per completion** | none |
| **CISPO** | G per prompt | like GRPO | ratio weight **capped**, tokens never switched off | none |

## PPO's version of the step

PPO wraps steps 6–7 in an **inner loop** that reuses the same batch K times (typically 2–4). Full details are in `04-ppo.md`.

```
                                                policy π_θ      value V_φ      reference   reward model
────────────────────────────────────────────────────────────────────────────────────────────────────────
1–2. generate completions; SAVE log-probs       used as-is         –              –            –
     ← these saved log-probs ARE π_old
3.   score → R                                      –              –              –         used (frozen)
4.   reference log-probs → per-token KL             –              –         used (frozen)     –
5.   value model predicts V at every token          –          used as-is         –            –
     per-token rewards (−β·KL, + R at end) → GAE → one advantage PER TOKEN
     (advantages now FIXED for this batch)
┌─── inner loop, K times ──────────────────────────────────────────────────────────────────────────────
│ 6. current log-probs (forward pass)            used              –              –            –
│    ρ = current ÷ saved π_old   (= 1 on inner step 1)
│    loss = clipped policy loss + value MSE loss
│    backward
│ 7. optimizer step                           ★ CHANGES ★     ★ CHANGES ★          –            –
└──────────────────────────────────────────────────────────────────────────────────────────────────────
→ discard batch; back to 1 (new generation = new π_old)
```

### What changes when (PPO)

| Thing | Fixed for… | Changes when |
|---|---|---|
| π_ref, reward model | the whole run | never |
| π_old (saved log-probs) | one batch | each new generation |
| Advantages | one batch | each new batch (computed once, before the inner loop) |
| ρ (ratio) | – | every inner step (because the policy changes) |
| Policy, value model | – | every inner step |

## GRPO's version of the step

The same as PPO's, with the critic removed and the KL moved. Full details are in `05-grpo-and-modern-variants.md`.

```
                                                policy π_θ      reference (optional)   reward model / verifier
────────────────────────────────────────────────────────────────────────────────────────────────────────────
1–2. generate G completions per prompt;         used as-is              –                      –
     SAVE log-probs (= π_old)
3.   score → R                                      –                   –                 used (frozen)
4.   (if KL) reference log-probs                    –              used (frozen)               –
5.   per prompt: (R − group mean) / group std → one advantage per completion,
     copied to every token; FIXED for this batch.   No critic. KL NOT folded into the reward.
┌─── inner loop (K can be 1) ────────────────────────────────────────────────────────────────────────────────
│ 6. current log-probs → per-token ρ             used                    –                      –
│    loss = −[clipped(ρ × A) − β·KL], averaged over tokens, then completions
│ 7. optimizer step                           ★ CHANGES ★                –                      –
└────────────────────────────────────────────────────────────────────────────────────────────────────────────
→ new batch
```

- **If all G rewards are equal, every advantage is 0**, and that prompt contributes nothing to the gradient.
- With one gradient step per batch **and no minibatching**, ρ = 1, clipping never activates, and GRPO ≈ RLOO with z-scored advantages. (Minibatching alone can make ρ ≠ 1. See lecture 4 `02`.)

## Lecture complete

The punchline (`05`): every algorithm is the same policy gradient, differing in **what Ψ is**, **how updates are bounded** and **how many models it needs**. Data and reward quality matter more than which algorithm you pick.
